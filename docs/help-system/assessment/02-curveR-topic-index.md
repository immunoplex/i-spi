## Amendment 2026-10-09 — `curveRmetrics` is out of scope

`curveRmetrics` was in scope when this phase originally ran. It has since been removed from the curveR ecosystem this assessment covers — the scope is **`curveR`, `curveRcore`, `curveRfreq`, `curveRbayes`, `curveRweights` only**, matching the plan's original assumption. The 7 `curveRmetrics`-only topic rows (QC metric definitions: inflection point, assay sensitivity, LOD, RDL, MDC, curvature-based LOQ, and the cross-method QC comparison overview) have been **removed** from §1's table below rather than left in with a "do not use" label, since they're not content material for Phase 2 authoring. Two rows that *mixed* `curveRmetrics` with in-scope packages ("Shape-LOQ vs. pcov-LOQ", "Quality metrics overview") have been trimmed to their in-scope package(s) only. §0.2 and §0.6 below are left as the historical record of what was found (including the now-resolved detection-limits overlap question) rather than deleted — §0.6 is in fact resolved *by* this scope change: `curveRcore::compute_detection_limits()` is simply the source now, no more ambiguity to verify. The topic count in the title/acceptance-criterion language below (24 topics) is the original, pre-amendment count; §1's table itself reflects the current 17.

## 0. Key findings — read this first

### 0.1 `curveR`'s own vignette is the best single cross-cutting reference in the ecosystem

`curveR/vignettes/curveR-methods-comparison.Rmd` is not a quick-start — it's a ~3,400-line manuscript-style methods paper (matching the repo's `manuscript_calibration-curve-regression.bib`), covering model forms, frequentist fitting, Bayesian fitting, eligibility-gated selection, precision profiling (both frameworks), detection limits, a full prose **Discussion** section (identifiability, boundary estimates, agreement between methods, limitations), and — appended at the end — a full **Precision-Weighted Downstream Analysis** section covering `curveRweights` too. It is the only document in the ecosystem that explains *why* the pipeline is built the way it is rather than just *what* each function does. **Recommendation: this is the primary "about the statistics" link for the help system's landing/overview entry**, not `curveR`'s own README (which is just an install/quick-start) and not any single package's vignette. Its prose sections (Introduction, Discussion, the four Appendix intros) are closer to end-user-readable than anything else in the ecosystem; its code-heavy sections still need bridging.

### 0.2 `curveRmetrics` references `stanassay` in its *vignette body*, not just its DESCRIPTION

Phase 0 flagged `curveRmetrics`'s `DESCRIPTION` naming `stanassay` as the Bayesian package (confirmed stale — `curveRbayes` is active, `stanassay` is out of scope per your resolution). The same stale reference also appears in prose inside `Workflow.Rmd`'s Overview: *"as long as they follow the functional forms from accompanying `curveRfreq` or `stanassay` R packages."* Same drift, second citation — worth fixing both spots together whenever `curveRmetrics`'s docs get touched.

### 0.3 "Richards" is an alias for `loglogistic5`, not a separate model — resolves a plan ambiguity

`curveRbayes/DESCRIPTION` says it fits "logistic, Gompertz, and Richards models," which could read as a model this assessment hadn't accounted for. It isn't one: `curveRcore/vignettes/model-forms.Rmd` names `loglogistic5` "Five-Parameter Generalised Logistic (Richards / log-logistic 5PL)" directly, and `curveRbayes`'s own default `model_names` is `c("logistic4", "logistic5", "gompertz4", "loglogistic5")` — no function or model object is ever literally named "Richards" in code. Treat "Richards" as a glossary alias for `loglogistic5`, not a sixth model family.

### 0.4 Function-level docs carry almost no citable statistical references — everything is in the vignettes/bibs

`grep -rl "@references" R/` per package: **curveRcore 0/18, curveRfreq 0/9, curveRbayes 0/11, curveRmetrics 0/8, curveRweights 1/12** (only `curveRweights-package.R`, the package-level doc, not a specific function). `@examples` coverage is similarly thin outside curveRweights (8/12) — most usage documentation lives in vignettes, not roxygen blocks. **Implication for Phase 5:** when the mapping table's "candidate source material" column points at a specific exported function for a compute-decision, the *function's own* `.Rd` page is very unlikely to carry a citation — the vignette (or, for curveRbayes, `vignettes/references.bib`; for curveRcore, `vignettes/core_references.bib`; for curveR, `manuscript_calibration-curve-regression.bib`) is the only place citations actually live. curveRfreq, curveRbayes-beyond-its-bib, curveRweights, and curveRmetrics have **no dedicated `.bib` file of their own** — curveRmetrics's Overview cites authors inline ("Rajam et al.", "Daly et al.", "Jeanne L Sebaugh and P. D. McCray", "Sanz et al.") with no bibliography to resolve them to full references. Flagged as a gap for Phase 5's gap list.

### 0.5 curveRcore's `getting-started.Rmd` already explains concepts the app's help system duplicates

`correct_prozone()` (prozone/hook-effect correction) is documented in detail in `getting-started.Rmd` §"Preprocessing with `preprocess_standards()`" — and the app *already* has its own `help/settings/apply_prozone.md` note (found in Phase 0) covering the same control. Same risk Phase 1 flagged for the measurement-error toggle: two independently-maintained explanations of the same concept. When Phase 4/5 touch `apply_prozone.md`, point its `references` field at this vignette section rather than re-explaining prozone correction from scratch.

### 0.6 Possible functional overlap between `curveRcore::compute_detection_limits()` and `curveRmetrics`

Both packages compute LOD/MDC/RDL-family quantities: `curveRcore::compute_detection_limits()` (`$lods`, `$mdc_rdl` on the `calibration_result` object, documented in `getting-started.Rmd`) and `curveRmetrics::compute_loqs()` / `compute_mdc_rdl()` / `generate_lods()` (documented in `Workflow.Rmd`, reading from a database rather than an in-memory object). **Not independently verified whether these are duplicate implementations, a database-persistence wrapper around the same math, or genuinely different formulas** — this needs a direct comparison of the two functions' source before Phase 1's decision-point write-up for "detection limits" can say which one the app's QC display actually calls. Flagged rather than guessed.
